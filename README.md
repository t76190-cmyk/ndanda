# んだんだ — 仮説検証用プロトタイプ

「まだ市場の言葉になっていない、やりたい・困った・できる」をAIが翻訳し、相性のよい相手につなぐマッチングサービス構想の試作品。
完成品ではなく、**「変な自然文を投げたら、思わぬ相手とちゃんとつながるか」** の1点を検証するためのプロトタイプです。

## 開き方

`index.html` をブラウザで開くだけ（静的ファイル1枚、サーバー不要、GitHub Pages にそのまま載せられる形）。

## 実装したもの（P0の縦一本）

1. **ンダ投稿**：1画面で自由文入力＋予算・期限（任意）。巨大フォームなし
2. **構造化の確認・修正**：投稿本文から構造化候補を生成し、公開前にユーザーが確認・修正できる
   - フィールド：intent（依頼したい／提供できる／参加したい）／domain／テーマ／skills／budget／deadline／location／commercial_use／privacy_level／risk_flags（簡易表示）
3. **相性スコアと理由**：自分のンダと他ンダの相性をスコア（0〜98）と「なぜ合うのか」の短文で提示
   - キーワード一致ではなく、向きの相補性・テーマ・分野の近さ・能力と需要の対応・期間・雰囲気で評価
4. **「んだ」→「んだんだ」**：双方が「んだ」を押すと「んだんだ！ マッチ成立候補」と表示される

## 入口の年齢確認（本人の決定：「つけよ。無難が一番。テストやし」）

トップに年齢確認のゲートを付けました。軽い自己申告式です。

- 開くとまず年齢確認カードが出て、通らないと本体に入れません（本体は操作できません）
- 「私は18歳以上です」にチェックを入れて初めて「確認してはじめる」ボタンが有効になります
- **18歳未満の方はご利用いただけません**と明示。「18歳未満です」を選ぶと利用不可の案内が出て、入室できません
- 二段構えの注記付き：ここは自己申告のみで、**本人確認（身分証などによる確認）は、実際に相手と繋がる段階（段階開示の手前）で別途行う設計**。重い本人確認の実装は今はしていません
- プロトタイプの注記と矛盾しない見せ方にしています：確認結果はどこにも送信・保存されず、開いている間だけ画面の中で保持されます（同一セッション内の再読み込みでは再表示しません。新しく開き直すと再表示されます）
- テスト用に、フッターの「（テスト用：年齢確認をやり直す）」からゲートを出し直せます

検証（Playwright、年齢確認15項目すべてパス・JSエラーなし）：
- ゲート表示／18歳未満は利用できない旨の明示／本人確認は繋がる段階で強める注記／未チェック時は入室ボタン無効
- 「18歳未満です」→ 利用不可メッセージが出て入室できない
- チェック → 入室 → 投稿→構造化確認→公開→相性表示まで一通り動作
- 同一セッションのリロードでは再表示なし／テスト用リセットで再表示／新規セッションでは表示
- 第2段階フロー全体の回帰（33項目＋相性スコア）もゲート通過後にすべてパス

プレビュー追加分：`previews/10-age-gate.png`（年齢確認ゲート）／`11-age-deny.png`（18歳未満を選んだ場合の利用不可表示）／`12-after-gate-flow.png`（ゲート通過後の投稿・相性表示）

## 第2段階：段階開示の流れ（つながりの部屋）

サービスのキモ「匿名で繋がった後に、条件が合った人とだけ、ちゃんと繋がる」を、P0の後ろに接続しました。

1. **匿名フェーズ**：広場では全員が匿名。見えるのはンダの本文と構造化された条件だけ（カードに「匿名」タグ、秘密候補には🔒タグ）。名前・連絡先はどこにも出ません
2. **条件のすり合わせ**：んだんだ成立後、「つながりの部屋」で双方の構造化条件（向き／分野／テーマ／能力／予算／期限／場所／商用利用／公開範囲）を並べた表で確認。各行に「一致／確認ポイント」を表示
3. **合意メモ（成立ンダ）**：双方が「この条件で合意する」を押すと成立ンダになり、双方の要望（ンダ本文）と全条件をまとめた「合意メモ」が自動生成され、双方に同じ内容が見えます（法的な契約書ではない旨を明記）
4. **相手の要望の最終確認**：合意の次に、相手の要望（ンダ本文＋全条件）だけを抜き出したパネルで「相手の要望を確認しました」を双方が明示的に示します。自分の条件への合意とは別のステップとして独立させています
5. **NDA共有（秘密候補のペアのみ）**：双方の要望確認が済むまでNDA確認ボタンは出ません（「双方が相手の要望を確認した上で共有します」とゲート表示）。要望確認後に「合意メモの内容について、秘密保持に同意する」ボタンで双方が確認するまで詳細開示に進めません。NDA文面そのものは置かず、導線と表示のみ（法務確認前のため）
6. **情報の段階開示**：成立ンダ＋双方の要望確認（＋NDA確認）後に、第1段階＝表示名とひとこと、第2段階＝連絡先（双方が「開示する」を押したときだけ互いに見える）。開示情報はすべてダミーデータ

> 最終順序は本人の確定事項：「**最後に相手の要望を確認した上でNDA共有**」——①双方の要望・取り決めの確認と合意 → ②その上でNDA共有（合意した内容＋秘密保持を双方で確認）→ ③段階開示
7. **匿名のまま見送る（断る）**：条件確認の段階に「今回はやめておく（匿名のまま）」導線。断るとマッチは終了し、名前・連絡先は相手に一切伝わらず、理由を伝える必要もないことを画面で明示。「断っても傷が浅く済む」ことを設計として伝える文言を各所に配置

デモの通し確認（Playwright、計33項目すべてパス・JSエラーなし）：
- A×B（公開同士）：匿名 → んだんだ → 条件表 → 双方合意 → 合意メモ生成 → 相手の要望の最終確認（双方）→ 表示名開示 → 双方了承で連絡先開示。要望確認が済むまでプロフィールが開かないことを確認
- F×G（Gが秘密候補）：合意 → 合意メモ → 要望確認が済むまでNDA確認ボタンが出ないこと → 要望確認後にNDA共有 → NDA確認が済むまでプロフィールが開かないことを確認
- C×D：匿名のまま見送り → 終了表示になり、相手の素性が画面のどこにも出ないことを確認（相手側が見送った場合の表示も確認）
- P0の回帰：相性スコア（A-B 61／C-D 69／F-G 62／E-需要文 70）は不変、投稿フローも正常

## 構造化・相性判定の実装について

検証環境のため、本番個人情報も外部AIのAPIキーも使っていません。
構造化と相性判定は、プロトタイプ用の**ローカルルールベースロジック**（カテゴリ推定・条件抽出・相補性スコアリング）で実装しています。
将来の本番では、この構造化部分をLLMに置き換える想定です（インターフェースは `analyze()` / `compatibility()` の2関数に分離済み）。

## テストンダと検証結果

資料のテストンダ A〜G を初期データとして組み込み済み。相手からの「んだ」が入った状態（B→A、D→C、G→F）をデモ用にプリセットしています。

| ペア | スコア | 主な理由 |
|---|---|---|
| A（村のPR）↔ B（1ヶ月仕事したい） | 61 | 向きの相補／分野の近さ／期間一致（約1ヶ月）／温度感 |
| C（ラーメン5杯必須）↔ D（無限にラーメン食いたい） | 69 | テーマ一致（ラーメン）／分野一致／大食い能力が需要に応える |
| F（団地で寂しい写真）↔ G（レトロな服を撮ってほしい） | 62 | 分野一致（撮影）／雰囲気の近さ（ノスタルジック・作品性） |
| E（カブトムシ山案内）↔ 需要文「子どもに本物のカブトムシを見せたい」 | 70 | テーマ一致／分野一致／山案内が需要に応える |

- 期待ペアはすべて候補の上位に来ることを確認済み。関係の薄いペアは最大36点までで明確に分離
- E のようなニッチ能力も、需要文が投稿されれば拾えることを確認済み（投稿フォームの「試す」チップからその場で試せます）

## 残課題（P1以降）

- intent 推定はルールベースのため、「したい」の主体（自分がやる／相手に頼む）の判定が外れるケースがある（ユーザーが確認画面で修正できる設計で吸収）
- 「求める能力」と「自分の能力」の分離（例：C の「食べられる人必須」は需要側スキルとして別フィールド化が望ましい）
- P1：公開範囲「限定」の運用（誰に見せるかの制御）、不適切・危険な投稿の抑止導線の本格化
- P1：サイト内メッセージ（段階開示の先のやりとり）、見送ったマッチの再マッチ防止などの運用ルール
- 合意メモの保存・ダウンロード（現状は画面表示のみ。状態はメモリ上のみで、再読み込みでリセットされる）
- 後回し：決済・NDA電子締結・外部サービス連携、本人確認。NDA文面は法務確認後に設定
- ブランド名・語彙は商標・ドメイン調査前の仮置き
